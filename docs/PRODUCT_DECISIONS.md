# 产品决策与验收口径

## 用户真正需要知道什么

目标用户已经有关注公司与研究判断，需要把具体条件交给系统持续检查。产品首先回答三个问题：规则有没有理解对、监控是否在正常进行、这次为什么提醒或没有提醒。

核心流程因此保留“生成规则 → 人工核对 → 激活”。首页展示任务、最近检查和状态；任务中的“查看依据”展开逐条件结果。所有控制项围绕这条流程组织，不以金融问答或荐股内容替代监控本身。

## 三条可行路线及当前选择

| 路线 | 主要收益 | 代价与适用范围 |
| --- | --- | --- |
| 纯规则监控 | 条件清晰、结果稳定，易于验证 | 自然语言覆盖有限；适合作为无模型时的回退 |
| AI 提取 + 确定性执行 | 能理解更自然的表达，执行与审计仍然可控 | 必须做结构验证和用户核对；这是当前主链路 |
| 自主投研 Agent | 可连接更复杂的研究、事件归因和多步任务 | 对工具稳定性、评测和责任边界要求更高，超出本次交付范围 |

## 关键机制

**信任来自每次检查。** 未触发也记录条件值、来源、时间和比较关系，不能只记录成功提醒。来源失效显示“无法判断”，有效的其他条件继续检查。

**低打扰不能丢事件。** 冷却只影响通知节奏，检查仍然进行。新公告进入待提醒队列；满足规则后才随提醒事务写入已处理指纹。

**公告与价格采用不同去重。** 同一公告以事件身份去重。价格属于持续条件，按规则版本和交易日最多提醒一次；用户改变规则会形成新版本，但已有冷却仍然生效。

**事件条件有明确含义。** 当前公告条件表示任务有效期内有尚未提醒的匹配事件。AND 规则将该事件状态与本轮其他条件组合判断，不承诺公告与价格变化发生在同一毫秒。需要“公告之后10分钟内跌幅”之类时序规则时，应扩展任务模型，当前不应强行编译。

**一个可操作的故障验证台。** 评审可主动注入超时、过期、冲突和重复公告，检查产品如何解释与恢复。每次注入都留审计记录，只允许影响演示任务。这使长程运行机制能在短演示里接受检查。

## 指标如何定义

| 指标 | 可复现定义 | 当前证据 |
| --- | --- | --- |
| 规则编译匹配 | 输出字段与预先定义的用例期望相符 | 固定20条；模型与回退分开记录 |
| 条件判断正确 | 同一规则与输入得到预期的三值结果 | 阈值、逻辑、休市、来源异常测试 |
| 无重复提醒 | 同一事件或当日同一版本价格条件产生的额外提醒数为0 | 重复检查、冷却、并发和重启测试 |
| 审计覆盖 | 实际完成的检查均有对应决策记录 | 连续50次检查与50条记录核对 |
| 中断恢复 | 进程重启后已提交任务状态一致，待提醒事件仍可送达 | 独立进程强制终止与恢复实测 |
| 用户留存与实际漏报率 | 需要真实用户和完整参考事件流 | 本次未测，不能从演示推导 |

## 提交前自己操作一次

用全新浏览器会话打开产品，创建黄金任务，修改一个阈值，然后依次运行正常行情、触发、重复事件、来源超时与恢复。只看页面，确认自己能说明当前任务在做什么、为何这次提醒或未提醒。最后导出证据并核对其规则版本。
